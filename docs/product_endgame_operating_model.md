# Sports Terminal Product Endgame Operating Model

## Product north star

Sports Terminal should not become a sports encyclopedia with better styling. The endgame is an operating system for sports decision-making. Users should be able to search data, manipulate datasets, build custom workspaces, generate reports, monitor changes, discuss ideas, run fantasy workflows, and publish analysis using source-backed sports information.

## Three-layer architecture

The first layer is Core Terminal. This includes players, teams, seasons, games, rosters, awards, draft, transactions, contracts, stats, standings, playoffs, search, compare, reports, saved views, alerts, sources, and data health.

The second layer is Workspace Studio. This is the Excel-like layer where users build tables, formulas, joins, pivots, charts, scenarios, saved models, exports, fantasy boards, and report inputs from terminal data.

The third layer is Network. This adds fantasy rooms, entity-linked forums, creator workspaces, analysis posts, private groups, shared boards, comments, moderation, and feeds.

## UI endgame

The current sidebar is useful while building, but it should not be the final navigation model. The long-term UI should use grouped navigation, favorites, a command palette, workspace switcher, entity pages with consistent tabs, table action bars, source badges, and context drawers. Build Lab should eventually become internal admin infrastructure rather than a massive end-user surface.

## Workspace plan

Workspace Studio is the highest priority product layer after core data and entity pages. It should start with dataset selection, column picking, filters, sort controls, table state, and saved views. Then it can add formulas, joins, charts, scenario sheets, exports, alerts, reports, and community embeds.

## Fantasy plan

Fantasy should be terminal-native. The first version can start with manually entered leagues, scoring rules, rosters, and watchlists. Later it can add waiver boards, trade analysis, matchup labs, projection boards, fantasy alerts, shareable boards, and external league integrations.

## Community plan

Community should be data-native. Posts and threads should attach to terminal objects such as players, teams, games, award races, draft classes, transactions, fantasy boards, charts, reports, and saved views. Public community features require accounts, permissions, moderation, report abuse, spam controls, claim flags, and source labels.

## MVP exit condition

The local NBA MVP is complete when a user can search real NBA entities, inspect linked detail pages, build an Excel-like workspace, compare entities, generate a basic report, save a view, and understand the source status of every displayed field.
